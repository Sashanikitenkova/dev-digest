# Skills — architecture diagrams

Reusable, agent-linkable prompt blocks. A skill is **plain text and nothing
else** — no tools, no resources, no executable payload. That constraint is the
feature's security story, not a simplification: an imported skill is someone
else's instructions landing inside your agent's prompt.

---

## 1. Data model

`skills` and `skill_versions` shipped in migration `0000_init.sql`;
`agent_skills.enabled` is the one column this feature added (`0011`).

```mermaid
erDiagram
    WORKSPACES ||--o{ SKILLS : owns
    WORKSPACES ||--o{ AGENTS : owns
    AGENTS ||--o{ AGENT_SKILLS : "links"
    SKILLS ||--o{ AGENT_SKILLS : "linked by"
    SKILLS ||--o{ SKILL_VERSIONS : "body snapshots"

    SKILLS {
        uuid id PK
        uuid workspace_id FK
        text name
        text description "the skill's interface"
        text type "rubric|convention|security|custom"
        text source "manual|imported_url|extracted|community"
        text body "markdown, the prompt block"
        boolean enabled "is this skill usable at all"
        integer version "bumped ONLY by a body change"
    }

    SKILL_VERSIONS {
        uuid skill_id FK "composite PK with version"
        integer version PK
        text body "immutable — restore writes a NEW row"
    }

    AGENT_SKILLS {
        uuid agent_id FK "composite PK with skill_id"
        uuid skill_id FK "composite PK with agent_id"
        integer order "block order in the prompt"
        boolean enabled "does THIS link contribute a block"
    }
```

Two independent switches gate one block: `skills.enabled` (the skill itself)
and `agent_skills.enabled` (this agent's use of it). A linked-but-disabled
link keeps its `order`, so re-enabling restores its position.

## 2. Review-time resolution — the load-bearing path

Before this feature, `run-executor.ts` called `reviewPullRequest` without
`skills`, so `prompt_assembly.skills` was always `null`. This is the wiring
that makes the control experiment work.

```mermaid
flowchart TD
    start(("Run Review")) --> exec[runOneAgent]
    exec --> fetch[(agentsRepo.linkedSkills)]
    fetch --> gate{"agent_skills.enabled<br/>AND skills.enabled?"}

    gate -->|no| drop[skip this link]
    gate -->|yes| sortSkills[sort by order asc]

    sortSkills --> trust{"source == 'manual'?"}
    trust -->|yes| trusted["### name<br/>body"]
    trust -->|no| untrusted["### name<br/>&lt;untrusted source='skill:name'&gt;"]

    trusted --> blocks[formatSkillBlocks]
    untrusted --> blocks
    drop -.-> blocks

    blocks --> empty{"any blocks?"}
    empty -->|no| omit["omit `skills` key entirely"]
    empty -->|yes| pass["spread ...{ skills }"]

    omit --> assemble[assemblePrompt]
    pass --> assemble
    assemble --> assembly{"assembly.skills"}
    assembly -->|null| noBlock["Run Trace: no Skills block"]
    assembly -->|non-null| withBlock["Run Trace: '## Skills / rules'<br/>+ token badge"]

    style untrusted fill:#fde2e2,stroke:#c0392b
    style trusted fill:#e2f0d9,stroke:#4a7c2f
    style blocks fill:#dce8f5,stroke:#2c5f8d
```

`formatSkillBlocks` lives in `reviewer-core/src/prompt.ts` — not in the server —
so the studio and the CI runner (which resolves skills from the filesystem)
share **one** trust rule.

## 3. Import — nothing persists until you confirm

`POST /skills/import/preview` is a pure function. Abandoning or re-opening the
drawer can never leave orphan rows behind, because saving is a *separate* call.

```mermaid
sequenceDiagram
    actor User
    participant Drawer as ImportSkillDrawer
    participant API as POST /skills/import/preview
    participant Zip as zip.ts
    participant DB as Postgres

    User->>Drawer: choose skill.zip
    Drawer->>Drawer: read file → base64
    Note over Drawer,API: JSON body, never multipart —<br/>keeps the Zod-validation convention
    Drawer->>API: { filename, content_base64 }
    API->>Zip: parse central directory

    loop each archive entry
        alt name ends in .md
            Zip->>Zip: inflateRaw (capped bytes)
        else anything else
            Zip-->>Zip: { name, skipped: true }
            Note right of Zip: never inflated,<br/>never written to disk,<br/>never executed
        end
    end

    Zip-->>API: body + skipped[]
    API-->>Drawer: SkillImportPreview
    Note over API,DB: no write occurs here
    Drawer->>User: preview + "skipped, not executed" list

    alt User confirms
        User->>Drawer: click "Import skill"
        Drawer->>DB: POST /skills (source: imported, enabled: false)
        Note right of DB: arrives DISABLED until vetted
    else User abandons
        User->>Drawer: close ✕
        Note right of Drawer: nothing was ever stored
    end
```

The skipped-files list shown to the user is **generated by the server**, not
guessed by the UI — so the guarantee displayed is the same fact the parser
acted on.

## 4. Version lifecycle

Narrower than the agents module's `isConfigChange`: only `body` snapshots,
per the `skill_versions.body` column.

```mermaid
stateDiagram-v2
    [*] --> v1 : POST /skills
    v1 --> v1 : edit name/description/type/enabled
    v1 --> v2 : PUT with changed body
    v2 --> v2 : edit metadata only
    v2 --> v3 : PUT with changed body
    v3 --> v4 : Restore v1

    note right of v1
        Metadata edits do NOT bump.
        Only a changed body writes
        an immutable skill_versions row.
    end note

    note right of v4
        Restore = PUT with the old body.
        It creates a NEW version —
        history is never rewritten.
    end note
```
