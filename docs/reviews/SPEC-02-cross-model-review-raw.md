## Verdict

No. The plan leaves the 8,000-token ceiling unenforceable over the actual provider payload, permits cache races and paid-call retries that violate the one-call-per-state requirement, and does not fully define or test reference validation for valid-but-unresolvable shapes. An implementer following it literally can produce stale or over-budget requests, spend multiple calls for one state, and store/render references that do not meet the grounding contract.

## Blocking problems

1. **The token budget is counted over only the user prompt, not the assembled model input.** Step 9 builds `buildBriefUser(...)` and passes that text to `shedToBudget`, whose counter is `container.tokenizer.count`. The subsequent `completeStructured` call adds `SYSTEM_PROMPT` and a JSON schema, both of which consume model-input tokens. Provider message framing may also add tokens. This violates AC-13’s ceiling on the assembled prompt and makes the claimed hard 8,000-token limit false. The plan’s T10 only proves a counter was invoked for shedding, not that it counted the actual payload. Fix: define the precise budgeted serialization as the system message, user message, and exact schema representation supplied to `completeStructured`; count that complete payload with `Tokenizer` after every trimming mutation. Reserve/count provider-required framing deterministically if it is part of the model input.

2. **There is no valid behavior when mandatory input alone exceeds 8,000 tokens.** AC-14 forbids removing title, author, branch, base, counts, all changed-file paths, risk scan output, L03 intent, blast summary, and impacted endpoints. On a PR with enough changed paths, endpoint strings, risk output, or an unusually large stored intent/blast summary, those mandatory sections can exceed the budget before any removable section exists. Step 6 nevertheless says shedding stops once it fits, while T10 explicitly permits an “absurdly small budget” while retaining all protected content. The result cannot both fit and retain the protected fields. Step 9 will either call above budget or need to drop protected content contrary to AC-14. Fix: escalate this specification contradiction before implementation and define one permitted outcome—for example, bounded representations for mandatory inputs established before assembly, or a defined no-call/failure path. The plan cannot invent a truncation rule because AC-14 says those fields are never removed.

3. **The arbitrary project-context-agent cap silently omits required prompt input.** Steps 5 and 9 introduce `MAX_CONTEXT_AGENTS`, then resolve paths for enabled agents “deduped and capped.” Neither the cap value nor deterministic selection order is specified, and omitted paths are not recorded as removed or unavailable. AC-11 requires the resolved project-context document paths as an input; AC-15 requires a ledger of what was present, removed, or unavailable, with reasons. This cap can silently change the brief and make provenance false. Fix: do not cap resolved inputs outside the specified budget-shedding procedure, or obtain a spec change defining deterministic capping plus ledger status/reason and its interaction with AC-14.

4. **Cache lookup and write are not concurrency-safe, so one PR state can produce multiple paid calls.** Step 9 performs a read for a matching head SHA, then independently generates and upserts. Two concurrent ordinary `POST /pulls/:id/brief` requests with no cached row, or with a stale row, can both miss the cache and both call the model. This violates US-4 and the non-functional requirement of at most one model call per distinct PR state. EC-12’s last-write-wins statement concerns overlapping explicit regenerations; it does not authorize duplicate normal cache-miss generation. Fix: define server-side single-flight/durable generation coordination keyed by PR and head SHA, including behavior for waiters and failures. The ownership must extend across process instances if the deployment can have more than one server process.

5. **A successful model call followed by a cache-write failure causes repeat billing for the same state.** Step 9 calls the model and only then upserts. If `upsert` fails, no durable result records that the paid call happened. The next ordinary POST sees no current cached brief and calls again. This violates the one-call-per-distinct-state guarantee, not merely availability. T13 tests only a failed GET read; it does not test write failure after a successful completion. Fix: define durable generation state/idempotency handling before the external call, including recovery semantics for a completed call whose final-record write fails. If exact once-only paid execution cannot be guaranteed across database failures, the plan must explicitly surface that as a specification conflict rather than claim the guarantee.

6. **A late older generation can overwrite a newer-head brief.** Step 8’s unconditional PR-keyed upsert and Step 9’s initial `pull.headSha` snapshot permit this sequence: generation A reads head `H1`; the PR moves to `H2`; generation B creates and stores a correct `H2` brief; A finishes and overwrites the row with `H1`. The UI will show it stale, but the current-state brief has been destroyed and a later normal POST must spend again. The plan’s assertion that a whole-row replace makes concurrency safe is incorrect; whole-row replacement prevents duplicate rows, not lost updates. Fix: make persistence conditional on the head SHA still being current, or use a generation/version token and reject obsolete writes. Define what the obsolete request returns.

7. **The cache key knowingly serves stale content as current for many inputs that are not the head SHA.** The plan treats `stored.headSha === pull.headSha` as sufficient freshness in Step 9. Correct brief content can change with the same head SHA when any of these change: PR title, body, author, branch, base, addition/deletion/file metadata, parsed diff/hunk coordinates or file rename metadata; stored intent; deterministic-risk implementation/output; repo-index/default-branch state and blast output; linked issue title/body or issue-fetch availability; enabled agents and their context attachments; workspace feature-model configuration; and possibly repository association/settings. A title/body/issue edit is especially material because it directly changes the stated “why,” yet the card will present the old brief without a stale notice because AC-50 also compares only head SHA. AC-3 requires the SHA cache hit, so this is a conflict between the stated input set and the claimed current brief semantics that the plan does not acknowledge. Fix: obtain a specification decision on what “PR state” means and whether head SHA is intentionally the sole freshness discriminator. If it is intentional, the UI/provenance must make clear that the brief is current only for the recorded head, not all current PR metadata; otherwise revise the cache versioning rule.

8. **The reference schema and validator leave line-only and null-valued references undefined.** Step 1 uses `.nullish()` fields with an unspecified “at least one is present” refinement. Depending on implementation, `{ file: null }` can pass merely because the key exists, despite naming no entity. Step 6 only says that a line is rejected when it is not in “its file’s” line set; it does not say that `{ line: 42 }` is dropped when no file exists. Such a focus item cannot be verified, cannot satisfy AC-26’s file-line relationship, and cannot meet AC-43’s required `file:line`/`file` rendering. Fix: require at least one non-empty, non-null entity value; reject any line unless a file is also present and the exact file/line pair validates; add explicit unit tests for `{}`, `{ file: null }`, `{ line: 1 }`, and mixed valid/invalid fields.

9. **The plan treats PR-authored title and metadata as trusted prompt text.** Step 7 calls the title/author/branch/base/counts line a “trusted header line,” although the specification’s provenance table marks PR title, body, author, branch, and base as untrusted and US-7 requires PR-authored text to be treated as data. A malicious title or branch name can therefore appear outside the injection delimiter and steer the model despite the system prompt’s untrusted-block rule. AC-54 explicitly enumerates body, issue text, and context paths, but does not authorize treating the remaining attacker-controlled PR fields as trusted. Fix: put all attacker-controlled textual PR metadata, including title, author, branch, base, file paths, and derived repo-controlled names, in appropriate escaped untrusted blocks, while keeping only server-authored labels and ledger statements trusted.

10. **The stored/API record contract omits required token metadata.** Step 1’s `PrRiskBriefRecord` includes provider, model, cost, and generated time but omits `tokens_in` and `tokens_out`, despite claiming AC-7 coverage. Step 4 adds those database columns, but `toBriefDto` is specified to return `PrRiskBriefRecord`; following the plan leaves the canonical record returned by GET/POST without both required metadata fields. Fix: add input and output token fields to the shared record contract and DTO, with names and types matching the database mapping, and test the route response as well as the raw row.

## Non-blocking concerns

1. **Hunk-header reduction has no deterministic retention policy**, from Step 6. “Progressively fewer files” does not say which files lose headers first. Different iteration order can produce materially different prompts and unstable briefs for the same state. Fix: define and test a deterministic ordering/selection rule while retaining every changed-file path as AC-14 requires.

2. **Reference rendering is underspecified for valid symbol-only or endpoint-only focus items**, from Steps 1, 6, and 16. AC-20 permits those shapes, but Step 16’s displayed focus format is only `file:line` or `file`, and its navigation algorithm is primarily file-based. Fix: specify text formatting for symbol-only and endpoint-only references and ensure those rows take the non-navigating path unless a valid GitHub target exists.

3. **The rate-limit test covers only one generation route**, from T18. AC-58 applies to each generation route, including `/regenerate`. Fix: exercise both route registrations or inspect their actual Fastify route configs through a focused test.

4. **The migration verification assumes all environments have zero existing `pr_brief` rows**, from Step 4. The lack of a current writer does not prove that every deployed or manually populated database has no rows. Nullable metadata columns avoid a migration failure, but the claim is not a valid verification condition. Fix: remove the unsupported assertion and test that a legacy/null-head row is treated as stale.

5. **The no-fetch verification is not meaningful security evidence**, from T15 and V11. Grepping the new module for HTTP symbols neither prevents a transitive helper from fetching nor proves model-output strings never reach a URL-capable API. Fix: test actual dependency calls with adversarial URLs in PR text, issue text, and model output.

## Gaps in test coverage

- AC-13 is not tested against the real complete payload. T10 does not include system-prompt tokens, JSON-schema tokens, or any provider serialization overhead, and it does not assert a final count `<= 8,000`.
- No test covers the mandatory-input-over-budget case, where all removable sections are absent or already removed but protected sections alone exceed the budget.
- T10 does not verify ledger entries and reasons for every present, removed, and unavailable section as required by AC-15. In particular, it does not cover budget removals, no-linked-issue, no issue number, context-agent cap omissions, or successful but empty optional inputs.
- AC-16 is mapped to T15, but T15 does not assert that the actual unavailable/removed ledger is included in the model prompt as trusted text.
- T2 positively checks selected allowed inputs but does not test AC-11’s “and only from” restriction. It would not catch extra data such as raw diff metadata/body through another assembly path, context-document text, unrelated PR history, or provider/configuration text being embedded in the user prompt.
- No test proves PR title, author, branch, base, changed paths, blast-derived paths, symbols, or endpoints are injection-safe. T15 covers only PR body and delimiter closure.
- T5 does not cover exact-match/path-integrity cases: case-changed paths, `./` prefixes, `..` components, slash normalization, renamed/deleted paths, a valid caller file with an invalid line, line-only references, null-valued fields, empty references, and references with multiple fields where one valid field must not rescue an invalid field.
- T5 does not directly test `buildAllowlist`’s complete required sources: changed files, changed-symbol names, caller file paths, top-level impacted endpoints, and downstream endpoint strings.
- T5 does not test the required `buildLineIndex` fallback when `newLineNumbers` is empty, so a drift from the grounding gate can pass.
- No test demonstrates that invalid model items are absent from every client rendering path, only that the normal card renders received items. A malformed/legacy stored row or a client-side transformation could reintroduce an invalid item.
- AC-2 is not directly tested for GET with both no stored brief and a stored brief while asserting zero LLM calls. T6 tests POST cache behavior instead.
- No test covers invalid UUID route parameters, workspace scoping/404 behavior, or GET’s primary-key read behavior.
- No test covers a stale legacy row with null `head_sha`, despite Step 4 relying on that state.
- No test covers concurrent ordinary POST cache misses, overlapping force/non-force requests, late obsolete writes, or write failure after a successful paid completion.
- T12 covers a thrown mock call but not timeout, schema-repair exhaustion, malformed structured output after repair attempts, or the requirement that the returned error names the feature and resolved provider/model while excluding provider response content.
- No test asserts the 1,200-token completion cap, 60,000 ms timeout, two-repair limit, maximum risk/focus counts, field character limits, or the $0.05 maximum cost.
- T18 does not verify `/brief/regenerate` is rate limited, nor that limits are per route/per IP rather than accidentally shared or bypassed.
- T11’s stated assertions do not verify card placement below the verdict banner and above—not inside—the existing two-column grid (AC-38).
- T11 does not explicitly verify the empty-state generate action invokes generation, the regenerate control invokes the force route, or that controls are disabled while their mutation is in flight (AC-49 and AC-51).
- T11’s stale test is not described as proving stale content remains rendered alongside the notice, rather than the notice replacing it.
- T16 does not test the actual `page.tsx` behavior required by AC-45: one `urlWith` invocation passed to one `router.push` containing all three keys. The plan explicitly admits this gap.
- T17 tests `SmartDiffViewer` in isolation, not URL parsing in the page, propagation through `DiffTab`, switching to the diff tab, and scroll behavior after navigation.
- No test checks all three synchronized registry copies and both full shared-contract trees are identical beyond the new file/platform file. The edited `brief.ts` copies are not included in V6.

## Questions the plan does not answer

- What is the authoritative representation whose token count must stay under 8,000: only user content, both messages, both messages plus the JSON schema, or the provider’s final serialized request including framing?
- What is the allowed outcome when non-removable required input is already over budget? The current AC-14/EC-15 combination provides no satisfiable implementation.
- Which hunk-header files are retained when progressively reducing headers, and is that ordering stable across runs?
- What is `MAX_CONTEXT_AGENTS`, which enabled agents win when it is exceeded, and why may their paths be omitted before the specified AC-14 shedding order?
- Is head SHA intentionally the sole cache freshness key despite title/body/issue/index/context/model-setting changes altering correct output? If so, is it acceptable to show such a brief as non-stale?
- How are concurrent non-force requests coalesced, and how is a request prevented from overwriting a brief generated for a newer head?
- What durable state prevents repeat charges after a successful provider response cannot be written to `pr_brief`?
- Does “exactly one LLM call per generation” mean one `completeStructured` invocation or one provider request total, given that `maxRetries: 2` can issue schema-repair reprompts?
- Are null, empty string, and line-only references valid under AC-20? If not, what exact validation rule rejects them?
- How should a review-focus item containing only a valid symbol or endpoint be displayed under AC-43, and should it ever be navigable?
- Is a workspace-selected model that can exceed $0.05 permitted? If not, where is price/cost admission enforced before the paid call?
